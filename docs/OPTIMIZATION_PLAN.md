# План оптимизации SubHub

Замеры от 2026-07-28 на рабочей копии. Главное правило плана: **поведение не меняется**.
Логин, покупка, OTP, гифт-карты, OOS-логика работают ровно как сейчас — оптимизируется
только занимаемое место и размер кода. Каждый шаг — отдельный коммит с прогоном
самопроверок из `scripts/test_*.py`.

## Что сейчас занимает место

| Что | Размер | Комментарий |
|---|---:|---|
| `chrome_profiles_done/` (19 профилей) | **1395 МБ** | 73 МБ на профиль в среднем, максимум 284 МБ |
| `.git` | 41 МБ | не трогаем — это история |
| `debug/` (34 PNG) | 27 МБ | скриншоты ошибок, без ротации |
| `vendor/` | 25 МБ | `ui-ux-pro-max-skill` 15 МБ + `system_prompts_leaks` 10 МБ |

Разбор одного профиля (96 МБ) показывает, что для входа нужен мизер, а остальное — кэш:

| Внутри профиля | Размер | Нужно для входа? |
|---|---:|---|
| `Default/Cache` | 24 МБ | нет |
| `Default/Code Cache` | 24 МБ | нет |
| `BrowserMetrics` | 25 МБ | нет |
| `GrShaderCache` + `ShaderCache` + `GPUCache` | ~12 МБ | нет |

Вывод: ~85–90 % объёма профиля — выбрасываемый кэш. Потенциал: **1395 МБ → ~150–200 МБ**.

## Приоритет 1 — диск, максимальный выигрыш при минимальном риске

1. ~~**Прунинг кэшей в профиле после закрытия браузера**~~ — **сделано.**
   Замер по 19 профилям: 1380 МБ, из них 1218 МБ (88 %) — кэши и скачанные
   Chrome компоненты. Остаётся 162 МБ. Чистка висит на `_close_browser_session`
   и доступна разово пунктом «Ч» главного меню. Проверено на живом профиле:
   после чистки (35 → 8 МБ) вход на Flipkart сохранился.

   Исходная постановка задачи:
   Точка врезки — `_close_browser_session()` в `menu.py`: после `ctx.close()` удалять
   `Cache`, `Code Cache`, `BrowserMetrics`, `GrShaderCache`, `ShaderCache`, `GPUCache`,
   `component_crx_cache`, `extensions_crx_cache`, `Variations`.
   **Не трогать** `Default/Network/`, `Default/Preferences`, `Default/Local Storage`,
   `Default/IndexedDB`, `Local State`, `.profile_meta.json` — там живёт сессия.
   Плюс пункт меню «почистить кэш всех профилей» для разовой уборки уже накопленного.
   Риск: низкий (кэш Chrome пересоздаёт сам). Проверка: после уборки профиль
   по-прежнему проходит `_flipkart_is_logged_in`.

2. **Не давать кэшу расти вообще** — флаги в `_browser_launch_kw()` (`menu.py:7043`):
   `--disk-cache-size=1048576`, `--media-cache-size=1048576`,
   `--disable-gpu-shader-disk-cache`, `--disable-gpu-program-cache`.
   Риск: страницы грузятся чуть медленнее (больше сетевых запросов). Делать **после**
   шага 1 и замерить время цикла покупки до/после — если заметно просядет, откатить
   только этот шаг.

3. **Ротация `debug/`** (~25 МБ): хранить последние 50 скриншотов либо удалять старше
   7 дней при старте. Риск: нулевой, это диагностические артефакты.

4. **Вынести `vendor/` из рабочего дерева** (~25 МБ): `ui-ux-pro-max-skill` и
   `system_prompts_leaks` в рантайме не используются. Сначала подтвердить грепом, что
   на них нет импортов, затем удалить и добавить в `.gitignore`.
   Историю `.git` не переписываем — это ломает OTA-обновления у клиентов.

## Приоритет 2 — размер кода

`menu.py` — **21 932 строки, 53 % всей кодовой базы**. Это уже мешает: правки в разных
экранах цепляются друг за друга, а поиск идёт по одному файлу.

5. **Выносить готовыми группами**, по одному модулю за коммит (механическое перемещение,
   без переписывания логики):
   - гифт-карты (`_parse_gift_cards`, `_select_gift_cards`, `_gift_*`, `screen_gift_cards`) → `subhub/gift_cards.py`;
   - куки и восстановление сессии (`_cookie_backup_state`, `_restore_profile_from_cookies`, `_console_offer_restore`) → `subhub/cookie_restore.py`;
   - подбор профилей и OOS (`_buy_candidates`, `_delete_oos_profile`) → `subhub/profiles_pick.py`.
   Страховка: тесты уже проверяют эти функции по имени и исходнику — после выноса они
   должны продолжать проходить, иначе вынос сломал контракт.

6. **Дубли `menu.py` ↔ `bot.py`** (`bot.py` — 4550 строк). Уже удалена 50-строчная копия
   парсера гифт-карт в пользу `_m("_parse_gift_cards")`. Пройти остальные вложенные
   функции `bot.py` и заменить копии на `_m(...)` там, где логика идентична.
   Риск: средний — у бота свои сообщения; сверять формат вывода до/после.

## Чего в этом плане сознательно нет

- Не переписываем контракты сообщений между слоями (`"OUT_OF_STOCK|DELETE_PROFILE"`,
  коды `OUT_OF_STOCK_2`, тексты «не залогинен») — на них держатся вызывающие.
- Не чистим `.git` и не пересобираем историю — от неё зависит обновление у клиентов.
- Не трогаем `data/` (карты, порядок оплаты, результаты) и `cookies_backup/`.
- Не занимаемся «красивым» рефакторингом ради красоты: только то, что даёт место.
